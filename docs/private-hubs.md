# Private hubs: development design

## Status

The macOS development build on `codex/private-hubs` now exposes password-based private hubs through **File → Create private copy…** and **File → Open private hub…**. The private gallery supports encrypted previews, notes/tag editing, per-video preview regeneration, automatic locking, password changes and verified unprotected copies. Follow the [first-build guide](./private-hubs-first-build.md) to try the workflow. These features are not part of the published 2.0.0 release.

Creating a private copy retains the original unencrypted `.scaena` file, previews, backups and source videos. The ordinary editor handoff saves pending drafts, pauses ordinary work and restores it after clean locking or cancellation. Native dialog, recent-document and single-instance adapters are controlled by the automated fixtures; broader platform and failure acceptance remains unfinished.

Touch ID is deferred from this first working build. Its implementation remains in the branch, but the unsigned app uses password unlock. Provisioned signing and interactive biometric acceptance are separate follow-up work.

The provisional format must not be used for irreplaceable data. Its compatibility contract will be fixed only after integration, recovery testing, and security review. The automated tests use synthetic catalogues and preview bytes.

## Intended protection

A private hub protects its catalogue, notes, tags, source paths, playback history, thumbnails, filmstrips, clip posters, and preview clips from casual filesystem browsing and from access to a copied, locked hub. The app decrypts requested records without mounting a filesystem of readable media files.

Original videos remain in their existing locations. External players, intentional exports, Finder handoffs, and clipboard actions can disclose content outside the hub. The operating system, a compromised application, or a person using an already unlocked hub can access displayed content. File count, encrypted sizes, directory names, and modification times remain visible. Whole-disk encryption remains useful for device loss and residual system data.

## Cryptography and key custody

Each hub has a random 256-bit data key. AES-256-GCM encrypts each record with a fresh random 96-bit nonce and a full 128-bit authentication tag. The hub identity, logical record identity, and format version are authenticated to reject record substitution. Plaintext is returned only after authentication succeeds; unknown formats fail closed.

Version 1 rejects substitution between different hubs or logical records. It has no trusted freshness counter: replacing a record with an older authentic version of that same record is not detected. Backups and explicit recovery intentionally retain older versions; rollback resistance is outside this first format's guarantees.

The password wraps the random data key. Version 1 uses Node's asynchronous scrypt implementation with a random salt and fixed parameters `N=131072`, `r=8`, `p=1`. This uses approximately 128 MiB for derivation, with a bounded implementation allowance. Fixed validated parameters prevent a modified header from requesting arbitrary work. Password text is not trimmed or silently normalized.

Scrypt is available in all supported Node runtimes without adding a native dependency. Argon2id remains an option for a later format revision; it must not be silently substituted for an existing format. Low routine overhead comes from retaining the unlocked key and reading only requested records, rather than weakening password processing. See [Node crypto](https://nodejs.org/api/crypto.html) and [OWASP password derivation guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Changing a password rewraps the data key; it does not rewrite every preview. Old copies of the key envelope may still work with the old password. Revoking access to those copies requires rotating the data key and re-encrypting the data.

Touch ID development is deferred while the password-based first build is reviewed. The retained implementation uses a device-local biometric Keychain item. The native module protects retrieval of the hub key and binds it to the complete current header. Enrollment requires the current hub password; disabling removes the local item without decrypting the hub. Password access remains available. The current unsigned build cannot use real Touch ID. See [Touch ID controls, signing requirements and remaining verification](./private-hubs-touch-id.md).

Owned key and working buffers are overwritten where practical. JavaScript strings, caller-owned decoded data, browser/GPU memory, swap, and crash dumps cannot be claimed to be securely erased by this code.

## Storage and recovery boundaries

Only the minimal versioned key header is readable. Record names use a keyed opaque mapping. Catalogue titles, paths, and preview identifiers must not be copied into the key header or directory name by future UI code.

Records and their temporary and backup copies contain ciphertext. Replacing an existing record first authenticates it, then preserves an encrypted backup. Invalid primary data must not silently replace a good backup. Recovery is explicit, rather than silently loading an older catalogue. POSIX directories and files use restrictive creation permissions. Windows private-hub storage is not implemented; it needs native locking and ACL support before it can be enabled.

The store rejects unsafe paths, symbolic links, and unrecognized hard links. The parent process opens a persistent empty lock file and passes its descriptor to a small native helper, which acquires an exclusive kernel advisory lock. Both processes retain the shared open-file description. The lock file is never deleted or replaced to reclaim ownership. An unexpected helper failure locks the store, wipes its owned key, and signals active media operations to cancel; the parent's descriptor retains the kernel lock until pending writes finish. If the parent exits, its descriptor and the helper's input pipe close; the helper then exits and the kernel releases the lock. No PID, hostname, or timeout-based stale-lock stealing is used.

The native helper requires the local-filesystem flag on macOS. Linux uses a conservative filesystem-type allowlist and rejects network and unlisted types. Native Linux execution and broader filesystem compatibility still need verification; current native tests run on macOS, including an actual packaged helper. The lock arbitrates cooperating applications. It does not defend against a hostile process with the same user's filesystem permissions racing directory replacement. Full directory-relative operations and signed/platform packaging acceptance remain integration work.

New-file publication uses an exclusive hard link followed by removal of a target-bound random staging name. If interrupted, a later read recognizes only exactly one in-root alias to that same inode. It authenticates the password/header or record ciphertext before completing publication. Wrong passwords, damaged ciphertext, unknown aliases, and external links cannot trigger cleanup. Process-kill tests cover this recovery path. Encrypted orphan files from work that never published remain untouched.

Catalogue and image records are authenticated as complete bounded buffers. Clips use 1 MiB authenticated chunks with an encrypted manifest, capped at 1 GiB per clip. A new immutable generation becomes visible only after its chunks are written and verified; a reader pins its generation so replacement cannot mix old and new bytes. Each requested chunk is authenticated before its requested slice is returned. The buffered preview API also uses this chunk format for clips; large playback requests should use range reads directly.

Old and interrupted generations are retained until a safe garbage collector is designed. Failures before manifest publication preserve the previous visible generation. A failure after the final filesystem publication can leave a valid new generation visible; reopen and authenticate to resolve uncertain completion rather than assuming rollback. Whole-catalogue JSON parsing still has significant memory overhead near its size limit.

The clip response adapter pins an authenticated generation before preparing length/range headers. GET supports one bounded byte range, including open-ended and suffix ranges; malformed, multiple, or unsatisfiable ranges return 416. Clip HEAD returns full representation headers without decrypting chunks; image HEAD authenticates the whole bounded record to establish its length, then discards it. Responses use `Cache-Control: private, no-store, max-age=0`, expose no validators or filesystem error details, and avoid eager plaintext prefetch. Locking, request cancellation, and a stale main-process authority predicate stop delivery. Already delivered bytes belong to the consumer and cannot be revoked. Private delivery is restricted to the isolated browser described below.

Locking invalidates store access immediately, prevents pending reads from delivering plaintext, discards the owned key, and drains pending storage work before releasing ownership. Data already returned to a caller remains that caller's responsibility. Storage locking alone does not lock the existing app interface.

## Protected preview generation

The new backend creates thumbnails, filmstrips, clip posters, and preview clips through memory pipes. FFmpeg receives an inherited open descriptor for each source read. Source filenames are absent from child arguments; the child uses the bundled tool directory and a small locale-only environment. FFmpeg reporting, source diagnostics, and inherited loader/configuration variables are not forwarded. Child stderr is discarded. Fixed plans restrict protocols to descriptors and pipes and do not accept renderer-provided filters or paths.

Each main-owned source capability binds a catalogue hash and exact source location to a mandatory grant/session predicate. It captures canonical root and file identity, size, and modification/change timestamps. Every decoder gets an independently opened descriptor, avoiding shared seek offsets. No-follow, nonblocking opens reject symlink or FIFO substitution; checks reject replaced roots, changed files, and revoked authority. The session additionally matches the capability to an exact primary or alternate location in its authenticated catalogue. The future activation coordinator must supply source permission grants and preserve grant-time root identity. Capturing a path is not itself a source permission grant.

One generation job runs at a time. Filmstrip frames are extracted sequentially and fed into one assembler; clips use one snippet encoder at a time feeding a remuxer. Image output is limited to 32 MiB, generated MP4 output to 256 MiB, and process handoff chunks to 64 KiB. Plans bound dimensions, screenshot counts, snippet counts, and per-child runtime. These limits bound application buffers and admitted work; they are not a hard memory sandbox for native decoders. Clips retain the first audio stream when present and support sources without audio. Source tags, stream metadata, chapters, subtitles, and data streams are omitted from generated output.

Generated images are validated for JPEG framing/dimensions, written as immutable encrypted records, and read back for comparison. Clip chunks use the existing authenticated streaming writer. The encrypted preview-set manifest is published only after all encoders close successfully and every member is stored and verified. Source/session authority is checked again after staging and immediately before atomic publication. Cancellation or failure before that publication preserves the previous set; a failure after filesystem submission may have committed and requires authenticated inspection. Cancellation also drains owned producers and descriptor leases before another job is admitted. Owned plaintext buffers are overwritten on release or revocation, subject to the memory-erasure limits above.

Private image and clip readers now resolve the active set, and each response pins the member it selected. Disabling clips suppresses both the old clip and its poster. A corrupt manifest, or a missing manifest with a surviving backup, cannot fall back to older previews. When both manifest and backup are absent, compatibility with initially converted encrypted previews remains available. Deleting all set references can therefore expose an older *encrypted* generation after unlocking; this is within the format's stated lack of rollback resistance and never permits plaintext filesystem fallback.

The session now owns generation admission and teardown. It derives extraction settings from the authenticated catalogue, admits one job, keeps catalogue reads available, and refuses saves while that job is active. Locking aborts generation synchronously and waits for its producers, descriptor leases, and storage work to drain. An accepted job consumes its source capability. Generated screenshot counts must match the existing catalogue entry before staging; changes requiring new catalogue geometry remain unavailable until a catalogue/preview transaction is implemented.

Per-video regeneration is connected through the private gallery and session-only native folder selections described below. Imports and changes to saved preview geometry still require catalogue/preview transactions. Custom thumbnail imports and damaged-file recovery/OS thumbnail fallbacks remain unavailable for private hubs until protected equivalents are implemented. No legacy extraction function may be substituted on failure. Descriptor-based access reduces incidental filenames and temporary-file exposure; it does not hide original media or decoder memory from the OS or sandbox FFmpeg against malicious input.

## Isolated browser and locking

Each capsule creates a new random Electron partition with caching disabled. It rejects the default session, persistent sessions, and any session with a storage path before adopting or clearing it. The window has no ordinary preload, Node integration, webviews, developer tools, or spellchecking. The credential window and unlocked gallery have separate, narrowly scoped preloads. The gallery bridge exposes only the authorized operations described below. Entry from the normal application uses the macOS native File menu and the saved-document transition.

The session serves only strictly validated `theatrum://app/` routes. Requests must belong to the capsule's window and current hub generation; frames, popups, downloads, navigation, device permissions, and display capture are denied. Static assets use bounded reads with file-identity checks. Content Security Policy restricts scripts, connections, images, media, and fonts, and disallows workers and frames. Headers suppress caching and referrers. These checks are installed before creating the renderer.

Offline emulation and WebRTC's `disable_non_proxied_udp` policy alone are insufficient: the native regression demonstrated a WebRTC TCP connection to its owned listener. The capsule additionally installs an unusable fixed loopback proxy, removes Chromium's implicit localhost bypass, and verifies that representative HTTP, HTTPS, WS, and WSS destinations cannot resolve to a direct route before loading the page. The final native run recorded zero connections to its TCP, HTTP, WebSocket, and UDP listeners. This is evidence for the tested routes and Electron version, not an operating-system network sandbox. Keep these probes when updating Electron. See [Electron sessions](https://www.electronjs.org/docs/latest/api/session) and [WebRTC IP handling](https://www.electronjs.org/docs/latest/api/web-contents#contentssetwebrtciphandlingpolicypolicy).

Hub revocation, system sleep or screen lock, renderer failure, window close, and app quit retire the capsule. It immediately revokes delivery and destroys the window without waiting for renderer cooperation or `beforeunload`, then independently attempts connection, storage, authentication, and cache clearing. App quit waits for those attempts. The capsule's own lock also drains hub storage and generation; callers initiating `hub.lock()` themselves must await that operation as well as the capsule's `closed` promise. Sessions are never reused. Cleanup failures are reported in capsule status, and a failed native window destruction prevents another capsule from opening until destruction is confirmed. Resuming the system never unlocks automatically.

Native macOS testing decoded a real synthetic encrypted JPEG, exercised browser storage, then locked, reopened, and restarted Electron against the same disposable profile. Cache size was zero and unencrypted UTF-8/UTF-16 markers were absent from scanned profile files. This does not establish erasure from memory, compressed data, swap, OS diagnostics, forced-crash artifacts, or every Chromium subsystem. Crash testing, real application assets, clip playback, and supported-platform verification remain necessary. See [the validation record](./private-hubs-validation.md).

## Password entry and opening

The unlock screen uses another fresh isolated window. Its protocol exposes only `index.html`, `unlock.js`, and `unlock.css`; it has no hub or preview authority. No selected path or hub title enters the document. The preload exposes only password submission, cancellation, a boolean Touch ID availability query and a one-shot Touch ID choice, without generic IPC, file, clipboard, or ordinary application methods.

Main-process credential handling accepts one response from the exact window's live main frame at the exact entry URL. Further navigation, a different frame/window, stale lifetime, malformed arguments, replay, and passwords outside the well-formed 1–1,024 UTF-8-byte bound are rejected. Whitespace and Unicode are preserved. The input clears before submission, on focus or visibility loss, and during teardown. The bridge's acknowledgement means only that the credential was accepted for handoff, not that authentication succeeded.

Submission destroys the credential window and disposes its IPC immediately. The password is handed to the opening coordinator only after browser cleanup succeeds and the transition remains authorized. Cleanup failures return no credential. JavaScript string copies and system memory remain subject to the erasure limits above. Incorrect passwords produce a generic unavailable result after session disposal; a fresh attempt is then possible. A prompt that has already submitted cannot be reused.

The opening coordinator admits one pending or live workspace per process. It captures a main-owned selected directory and transition authority, accepts a password or an enrolled Touch ID choice, unlocks the session, then creates the isolated hub window. It returns only an outcome and status, never the decrypted catalogue, password, source paths, or mutable browser/session objects. Cancelled late completions are adopted only for disposal; no late window may be shown. Reuse waits for all owned prompt, session, browser, generation, and storage work to drain. Unproven resource cleanup failures quarantine admission. Safe factory failures are recognized by a main-process error brand, not by matching error text.

In standalone mode the workspace observes sleep, screen lock, shutdown, and quit before opening begins and until its coordinator settles. This covers password entry and key derivation while no hub window exists, including the gap after credential-window destruction. External mode requires an AbortSignal and delegates system events and quit to the parent application transition. Both credential and gallery windows use the same ownership mode, preventing competing quit retries. Direct signal revocation still destroys private windows immediately. The native application factory composes this workflow with directory selection and normal pausing. The macOS File menu calls it directly; an unavailable result produces a generic retry message without revealing private paths or native errors.

## Main-process integration boundaries

`PrivateHubSession` owns the store and accepts generation tokens rather than renderer paths. A cancelled unlock invalidates immediately; a late successful store open is locked and discarded. Its lock observer runs after synchronous key and generation revocation, so a failed cleanup callback cannot retain key access. Explicit `close()` waits for storage and pending operations to drain before returning to idle. Locking alone never changes a private storage target into a normal target.

The session admits at most 16 outstanding preview responses with a 128 MiB reservation budget. An image reserves its 32 MiB maximum and a clip reserves one 1 MiB chunk before queuing any read. Delivery, cancellation, failure, and locking refund reservations exactly once. This bounds unread response admission without adding a stream wrapper or prefetch; it is not a total process-memory limit. Catalogue parsing, cryptographic working buffers, and data already handed to the browser consume additional memory. The gallery queues at most three image loads, including its detail poster, leaving reservation space for a requested clip. Image failures receive at most two retries. Pages contain at most 48 videos and off-screen thumbnails wait for visibility. Larger-library scrolling and memory measurements remain pending.

First activation verifies the conversion receipt and all copied content, then publishes an encrypted, hub-bound activation marker. Subsequent unlocks authenticate this marker and the current catalogue, allowing legitimate catalogue edits after conversion. Only a genuinely missing marker triggers conversion verification; a malformed or unauthentic marker fails closed. The marker records initial verification, not rollback resistance or proof that every preview remains undamaged forever. Each preview is still authenticated when read.

The common writer captures its main-owned storage target before preparing catalogue data. Private failures cannot invoke legacy backup recovery or create a plaintext catalogue. The protocol validates the app origin, preview type, hash membership, private-session generation, and active main-process authority; missing or corrupted private previews cannot fall back to leftover plaintext files.

Legacy renderer IPC remains unavailable in private mode. This prevents its existing settings, export, playlist, player, and extraction handlers from being mistaken for private-aware implementations. Normal metadata and `.vha2` exports also recheck storage/session identity after native save dialogs. The normal open workflow and source-connection monitor refuse private mode.

The main process now owns a separate normal-application pause boundary. It closes normal IPC admission before revoking asynchronous authority, pauses source reconnection checks, and stops extraction queues, crawlers, and watchers. It waits for native dialogs, catalogue/settings writes, playlist cleanup, native media completion, filesystem callbacks, and watcher closure. Cancelled timers or a process termination request alone do not prove that work has stopped. Late native picker results cannot grant paths, and callbacks from a previous operation cannot gain authority when normal admission reopens.

Ordinary preview requests also retain a scoped lifetime through canonical-path resolution, fetch, and body consumption or cancellation. Pausing aborts pending fetches and refuses late headers or chunks. The wrapper preserves ranges and response headers, does not prefetch, and caps live responses at 512. Its drain observes the settlement of JavaScript fetch/read/cancel promises, including rejected cancellations. Native Electron checks exercise unread and active streams, delayed native responses, renderer cancellation, and resumed delivery; these do not prove closure of Chromium's underlying file handles or erasure of browser/OS caches.

Pause succeeds only after every tracked subsystem has settled. A failed watcher close or restoration leaves admission closed; the caller must not open a private hub or silently resume normal work. Resuming consumes the pause proof and restores subsystem admission before reopening IPC.

The application transition first obtains a native directory selection, then pauses normal work before requesting a renderer snapshot. This ordering lets earlier scan/rename responses reach the renderer before its snapshot request. The dedicated exchange freezes editing, identifies the original frame and request with a one-use nonce, and waits for a full snapshot of every active writable hub. A dirty boolean or ordinary save notification cannot authorize private opening. The snapshot writer captures the normal destination and source/media authority, rejects remapped sources or invented media, and awaits an atomic save without writing private paths to settings or recent history. No-hub and read-only sessions use a null snapshot. A late save may finish its original write but cannot publish authority into a replaced catalogue.

Only a current pause proof and saved-document proof authorize password entry. The normal window remains held while the external private workspace is active. Clean private disposal precedes releasing the document and restoring the normal window; failed private cleanup retains the editing freeze and sealed normal admission. Window/frame identity and the pause proof are rechecked after restoration before admission reopens. Quit waits for this clean handback and retries the normal settings/catalogue close flow once. A host acknowledgement of Keep Working or close-save failure can restore future private admission; simply returning from `app.quit()` cannot do so.

The live renderer now uses a shared mutation gate for persisted edits, delayed confirmations and native results. Catalogue row-tag drafts commit before snapshotting; unfinished composition and pending native invokes refuse the handoff. The entire document becomes inert while paused. Late native responses are retained and replayed after main admission resumes, without marking the earlier snapshot clean. Failed restoration quarantines the renderer. Production-class tests exercise Home and its services. One native Electron fixture exercises the production renderer coordinators with real text insertion, browser input blocking, media playback and IPC. A second fixture runs the compiled Angular Home/catalogue editor with the actual preload, snapshot writer and private workspace; it verifies draft saving, isolated gallery editing, Lock, cancellation, draft/composition refusal, an actual atomic-write failure and intercepted quit/reopen. Its startup/source adapters and ordinary menu are synthetic. A further actual-main fixture verifies real watcher/scan recovery and ordinary close/save handlers, using the production macOS admission with fixture asset paths, a test driver and controlled OS adapters. The dedicated private windows own a restricted application menu; broader lifecycle faults, native picker history and platform editing behavior still require verification.

`main.ts` owns one allocation-free `PrivateApplicationWorkspace`. Close and shutdown handlers consult its active state before the ordinary settings/catalogue save handshake. A trusted, captured close operation reports Keep Working or a save failure to the main-owned quit acknowledgement; an old frame or catalogue cannot release a replacement session's quit state. Native catalogue-open requests received while paused stay in a bounded memory queue and acquire filesystem authority only after normal admission resumes.

After clean private settlement, a fresh ordinary scope sends `normal-workspace-resumed`, restores source monitoring and dispatches queued normal catalogue opens. Home clears interrupted progress indicators and scan state without discarding delivered catalogue edits or source grants. The native File menu registers opening and creation callbacks directly. `PRIVATE_HUB_UI_READY` restricts application entry to macOS for this first test build.

Private opening is exposed through the native File menu, without adding ordinary renderer capabilities. No ordinary renderer code can select the main-owned private storage target; opening credentials use the dedicated isolated prompt, and password changes use the isolated private gallery credential form. The connected normal-mode handoff, native selection, private gallery, settings policy, source grants, browser restrictions and packaged helper remain covered by separate unit and native acceptance checks.

## Private gallery and editing boundary

The gallery metadata bridge accepts only list/search, detail selection, notes/tag save, per-video regeneration, cancellation, protection-setting and lock requests. It binds to one private window, its exact main frame and entry URL, and one unlocked hub generation. A navigation (including a same-URL reload), frame replacement, crash, lock or disposal rejects later results. Issued selection and edit revision IDs are random and valid only within that browser lifetime. The standalone preload exposes no general IPC, subscriptions, filesystem, clipboard, source-path, password-retrieval or key API. The separate frozen `privateCredentials` surface provides `changePassword`, `createUnprotectedCopy`, `cancelUnprotectedCopy`, `touchIdStatus`, `enableTouchId` and `disableTouchId`. Submissions accept bounded credentials for the same private window and generation; they cannot retrieve credentials or alter another hub. Copy destinations come only from a main-owned native picker.

Lists contain at most 48 videos and search only titles and tags; deleted records and synthetic folders are omitted. Details reread the encrypted catalogue and verify the selected row's original index and source identity before refreshing the cached projection. Successful saves also refresh search metadata. The renderer receives notes and authorized encrypted preview URLs, without the full catalogue, source locations or original filenames. The display limit is 100,000 videos. Titles are limited to 2,048 characters, tags to 128 entries of 512 characters, and notes to 65,536 characters; details indicate shortening. Shortened or malformed notes/tags cannot be edited through this view, so saving cannot replace the original with a displayed subset. Title shortening alone does not prevent notes/tag editing.

Save submits only the issued selection ID, opaque revision, notes and tags. Main maps these to the original catalogue index and a private digest of the complete video row. The session reads, compares, edits and writes within one queue operation. A changed row produces a conflict; unrelated concurrent catalogue changes survive. Existing legacy tag strings remain exact, including duplicates in an unchanged tag array. Newly introduced tags follow the application's hierarchy rules. No source, preview setting, tag definition, colour or unrelated video field is changed. The original JSON object is preserved rather than saving the loader's normalized source settings.

The session reserves and wipes bounded request/output buffers, refuses concurrent preview generation, and passes a monotonic window/frame/generation guard through encrypted storage publication. Revocation rejects late success and prevents publication when detected before the filesystem operation. A write already admitted to the operating system may finish; reopen the hub to verify its saved state. Actual storage failures lock the session, while validation failures and conflicts retain the draft for correction or explicit Discard and reload.

Notes and tags remain drafts until Save changes. Selection, searching, paging and closing details refuse to discard a draft silently. Save and tag insertion wait for text composition to finish. Discard reloads the latest stored metadata. Lock hub remains available during edits and saves; its warning explains that drafts will be cleared and an in-flight save may finish. No plaintext sidecar, autosave or browser storage is used for edits.

The view uses literal text nodes for metadata, blocks copy/cut/drag/context-menu exports, and requests playback only after Play preview. Paste is accepted only in an active password field. Lock hub clears its visible text and media sources before requesting main-process revocation and browser destruction. These restrictions do not prevent OS screen capture or access through an already compromised process. The dedicated-window native controls are tested below; the complete normal-to-private workflow still requires native verification.

Choose **Show filmstrip** in the selected video's details to browse its saved frames. Scroll horizontally or use the previous/next controls. **Hide filmstrip** clears the image; opening it again requests the encrypted preview afresh. Missing or unreadable filmstrips show a generic unavailable message. Opening or hiding a filmstrip preserves unsaved notes and tags and does not start video playback.

Filmstrip URLs are supplied only with selected details, never list rows, and use the same authenticated, isolated media route as the other previews. The viewer shares the three-image loading queue, cancels retries when hidden and rejects stale callbacks after selection changes, regeneration, protection operations or locking. The encrypted image limit bounds encoded bytes; converted legacy JPEG dimensions are not currently bounded, so it is not a hard decoded-image memory limit. The view creates no plaintext media file, mounted volume or browser-storage copy. This does not establish OS/GPU memory erasure or prevent screenshots of an unlocked hub.

## Native menus, shortcuts and password paste

Private windows temporarily replace the application menu before opening any renderer. The restricted menu provides **Cancel unlock** or **Lock hub**, **Paste password**, **Select all**, Hide and Quit. It contains no Copy, Cut, Services or ordinary Window menu. Menu actions remain bound to that private window; an old menu cannot act on a later window. The exact prior application menu is restored only after the private renderer is destroyed and storage, requests and browser cleanup have finished successfully. A completion captured for the unlocked generation covers storage drainage even when another component initiates the lock. Uncertain installation, replacement or restoration keeps the restriction in place and prevents another private session from disguising the cleanup failure.

Copying, cutting and dragging text or previews out of both private screens is disabled, including when an unlock password is revealed. The main process also blocks export shortcuts before they reach the page or native menus, including conventional copy/cut shortcuts, legacy clipboard chords, shared Find and macOS kill-ring commands. Native menu accelerators are ignored by the private web contents; explicit paste, selection, close and quit shortcuts use the owned window and lifecycle. Ordinary typing, composition, selection and undo remain available within the document.

To enter a password, focus an enabled password field and use **Paste password** or the usual paste shortcut. Paste is rejected in notes, tags, search fields and inactive, concealed or pending credential controls. The renderer does not read clipboard data in its event policy, and main forwards the deliberate paste command without retrieving or retaining clipboard contents. Password paste was validated through synthetic DOM events; manual use of real OS clipboard contents remains an acceptance check.

Native verification installs an ordinary application menu before opening the real private screens. It checks replacement, exact restoration after clean teardown, and retention during held cleanup. Real Copy/Cut commands and keyboard shortcuts are exercised with a fixture-only backstop that always cancels default clipboard export, so the test can detect a missing production blocker without reading or replacing the user's clipboard. The test is macOS-specific. It does not establish Linux X11/Wayland selection-buffer privacy, Windows clipboard history behavior, OS Services outside these menus, accessibility isolation or screen-capture prevention. These remain platform and manual acceptance checks before entry is enabled.

## Automatic locking and Protection settings

In the development gallery, open **Protection**, choose **Auto-lock after**, and select **Save setting**. Available choices are Off, 1, 5, 15 and 30 minutes; a hub without saved settings defaults to five minutes. The choice is encrypted inside that hub and survives reopening. It does not enter ordinary app settings or browser storage. A malformed or unauthenticated settings record, or a missing primary record with a surviving backup, prevents opening instead of silently replacing the policy.

Typing, clicking and scrolling within the private window renew the deadline through Electron's native input events. Mouse movement, focus changes, page-generated events, IPC requests, playback and regeneration do not. Inactivity can therefore lock a playing preview or cancel generation. Locking clears unsaved edits, destroys the window and drains pending operations; an encrypted write already admitted to the filesystem may still finish. **Off** disables only inactivity locking. System sleep, screen lock and other lifecycle revocation still close the hub, and resume does not unlock it.

The main process checks the existing deadline before input or a settings change can renew or disable it. Changing the timeout preserves elapsed inactivity. Settings are authenticated before browser allocation; live changes take effect only after encrypted persistence succeeds. Reads and saves share the bounded gallery admission gate, and protection writes cannot overlap preview generation. Invalid or stale requests cannot resurrect a retired browser. Native clock, scheduler or authority failures retire access rather than leaving a readable window with a stopped timer.

The settings record uses the existing authenticated store and backup rules. Encryption does not prevent replay of an older complete hub snapshot. There is no trusted monotonic policy counter; removing both settings records is indistinguishable from a hub that has not saved a setting. The provisional format and recovery policy still require review before use with real hubs.

## Change a private hub password

In the development gallery, open **Protection → Change password**. Save or discard any video edits and apply or restore any unsaved auto-lock selection first. Enter the current password, enter and confirm a different new password, then choose **Change password and lock**. Password text is preserved exactly, including whitespace and Unicode; well-formed values must contain 1–1,024 UTF-8 bytes. An incorrect current password leaves the hub available for another attempt. Successful changes lock the hub; use the new password when reopening it.

The form clears all three fields before submission, including locally invalid submissions. It also clears them when collapsed, when Protection closes, on focus or visibility loss, and during locking. Playback stops before the request. Video drafts survive refused changes, and editing, regeneration and settings writes cannot overlap an admitted change. Lock remains available while authentication or storage is pending. Inactivity, sleep and other existing revocation rules still apply.

The main process validates the exact live frame and uses a dedicated, fixed credential channel sharing the gallery's admission gate. It reauthenticates the saved header, verifies that the resulting key belongs to the active store, and wraps the unchanged data key with the new password and a fresh salt/nonce. Header replacement is atomic under the existing lease and path checks; the newly published inode and bytes are verified before success. No old-password header backup is created. Unexplained local header backups or staging copies prevent a change rather than being deleted or silently retained as an alternate password.

Session-owned queued credential buffers are wiped on lock and immediately after passing them to storage. Owned derived keys are wiped after use, and string references are released promptly; JavaScript strings, Electron IPC copies and operating-system memory cannot be reliably erased. The renderer receives only a bounded result, never passwords, keys, header bytes or paths. After success, the main handler independently locks the session before invoking window cleanup and waits for the storage drain. Failed cleanup quarantines normal-mode restoration.

A failure after a filesystem publication has been admitted can leave either password active. The session locks without reporting success; reopen to check which password is accepted. Do not replace the header manually or remove leftover files as a recovery shortcut. Earlier copies of the hub or its old key envelope remain usable with their old password, including against later records using the same data key. This operation does not rotate that key or remove backups. Revoking old copies requires a separately designed re-encryption operation.

## Source access and preview regeneration

Select a video and choose **Regenerate previews** to replace its encrypted thumbnail, filmstrip, clip poster and enabled clip. Save or discard notes/tag drafts first. The native folder picker asks for the exact preferred source folder saved in the encrypted catalogue. This workflow does not relocate a missing source or choose an alternate location. Duplicate video hashes and unsupported preview geometry remain unavailable.

The main process keeps a bounded source grant in memory until the private browser closes. No app filesystem probe occurs before the first explicit folder selection. Subsequent jobs recheck the canonical root and its device/inode identity; replacement or disconnection invalidates the cached grant. Selecting the folder again requires another explicit regeneration action. Source paths, bookmarks and access decisions do not enter renderer IPC or ordinary settings. The app does not revoke macOS permissions when its in-memory grant expires. Native picker history and platform permission behavior still need manual verification.

Regeneration accepts only an issued video ID and opaque revision. Main rechecks the complete saved video row after the picker closes, captures a no-follow descriptor capability, and derives generation settings from encrypted storage. It does not change the original file or catalogue metadata. Source capabilities recheck file/root identity, size and timestamps, but are not a filesystem sandbox against a hostile process running as the same user.

## Safe conversion requirements

The conversion API creates a separate destination and requires a synchronous main-process assertion that source writers remain paused. An asynchronous assertion is rejected. It snapshots the catalogue and generated preview files, copies them through memory, verifies decrypted destination hashes, then rechecks source file identity, size, timestamps, directory state, and missing-file state before publishing the encrypted receipt. Progress events contain stages and counts only. The API never opens original videos or follows their stored source paths.

Before conversion, `reviewCatalogueForPrivateConversion` reads the catalogue and preview metadata and returns immutable counts for referenced videos, available previews, preview bytes and missing previews by kind. It never opens preview payloads or original video paths and creates no output. Main must hold source writer exclusion from review through conversion. The issued review is single-use and bound to the exact catalogue content, file/directory identities, present/missing inventory and source-exclusion lifetime; a clone, stale review or replay cannot authorize conversion. Only count-only display data crosses the isolated conversion bridge; the proof itself stays in main.

All existing referenced preview types are copied. Missing thumbnails/filmstrips, and missing clips when clip generation is enabled, require explicit `allowMissingPreviews` authorization with that issued review and are recorded inside the encrypted receipt. Disabled and absent clips do not require that override. Unreferenced previews, prior plaintext catalogue backups, and regeneration leftovers remain in the untouched original tree; this copy operation does not eliminate their exposure.

Cancellation, source changes, and failed verification leave the original authoritative and retain an encrypted incomplete destination. The completion receipt is published last. An error after that publication can still leave a valid completed copy; `verifyPrivateHubConversion` reauthenticates the receipt, catalogue, inventory, and every preview after reopening. Receipt verification describes the initial copy, not a perpetual digest of a hub after subsequent legitimate edits.

Conversion confirms its owned source descriptor closures, producer/verification iterator returns and final store-lock settlement before reporting completion. Individual descriptor/iterator cleanup has a five-second deadline; final store drainage has a separate thirty-second deadline that allows its sequential lease shutdown. Failure or timeout produces a main-process identity brand that remains a failure after late success. First activation retains this uncertainty through session disposal and the outer application transition, preventing ordinary work from resuming. The completion receipt may already exist, so failure does not imply that the copy was unpublished.

Store-owned file and directory handle closures now have their own five-second confirmation deadlines. Lease cleanup confirms helper shutdown and descriptor closure separately. Failure or timeout revokes keys/admission, retains a process-local directory quarantine, and stays identity-branded through create/open, Touch ID availability, session disposal and conversion verification. A later successful close cannot clear it. Ordinary read/write failures remain distinguishable when all cleanup is confirmed.

These deadlines start only when cleanup begins; they do not bound a stalled source read or iterator advance. Lease shutdown allows five seconds for graceful exit before requesting termination, then five more seconds to confirm helper closure; its parent descriptor has a separate five-second deadline. These JavaScript/native-helper observations do not prove OS cache erasure. The conversion UI/controller now has bounded actual-host coverage for saved drafts, late-picker cancellation, verified activation and ordinary restoration. Broader native fault acceptance remains follow-up work for the experimental workflow.

A failed or interrupted conversion preserves the original hub. The development coordinator pauses ordinary writers and saves drafts before conversion, keeps the ordinary renderer frozen through copy and activation, and reopens/verifies the completed destination before showing its private gallery. Cancellation or Lock returns to the original ordinary workspace only after confirmed private cleanup. Incomplete destinations are never presented as ready hubs. Do not delete plaintext originals or their backups as a side effect of enabling an experimental setting. Once a verified destination is active, removal of old copies must be an explicit user decision that explains the limits of SSD deletion, snapshots, and earlier backups. Removing protection similarly requires authentication and a verified destination; it is not an in-place toggle that risks both copies.

## Create an unprotected copy

In the development gallery, save or discard video edits, open **Protection**, and expand **Create unprotected copy**. Enter the current password, acknowledge the plaintext warning, and select **Create unprotected copy**. After authentication, choose a new destination folder in the native dialog. Existing folders cannot be replaced. The encrypted hub stays open and is kept, along with all original videos.

The destination contains `<hub name>.scaena` and the ordinary `vha-<hub name>` preview folders. The catalogue is preserved byte for byte, including notes, tags, source references and unknown fields. Only referenced preview identities are exported. The current authenticated generated set takes precedence over older previews; disabled clips stay disabled. A genuinely absent legacy preview remains absent, while corrupted records, backup-only records and missing members of a current set stop the copy. No source video is opened and no missing preview is regenerated.

The copy uses new owner-only directories and files, exclusive creation, bounded authenticated clip streaming and verified readback. It rechecks the catalogue and preview identities before publishing the `.scaena` file last. Source writers remain paused during authentication, destination selection and copying. The password buffer is cleared before the destination picker opens; password fields and acknowledgement clear at submission and on concealment or focus loss.

**Cancel copy**, manual locking or automatic locking stops further work once observed. An operation already admitted to the filesystem may finish. An interrupted copy can leave ordinary unencrypted files, including a completed catalogue, in the selected folder. These files are retained; cancellation does not claim to erase them. Failure to confirm descriptor or iterator cleanup quarantines the session and blocks restoration. The original encrypted hub is never deleted or converted in place.

Creating this copy deliberately exposes its catalogue and previews to ordinary filesystem access, indexing and backups. It does not remove or change encrypted copies, source videos, prior exports or OS snapshots. The operation uses no plaintext staging outside the chosen destination and never hands the output to Finder or an external player automatically. Actual native picker history and the complete application workflow still require manual verification.

## Continuing acceptance coverage

- Wrong passwords, changed headers, unknown versions, corrupted tags, truncated records, record swaps, and hub swaps fail without plaintext fallback.
- Faults during save, backup, conversion, and recovery preserve the authoritative original. Private operations never stage plaintext outside an explicitly selected unprotected-copy destination.
- Locking during asynchronous work prevents stale responses, new writes, permission prompts, and background extraction from restoring access.
- Repeated open/close, concurrent processes, stale locks, symlink changes, and oversized inputs have defined safe outcomes.
- A recognizable synthetic marker in filenames, notes, paths, and preview bytes is absent from unencrypted app storage, temporary files, caches, logs, and recent history after normal use and a simulated crash.
- Optional external handoffs and the original-media boundary are correctly described. No claim of guaranteed screen-capture prevention or complete operating-system invisibility is made.
